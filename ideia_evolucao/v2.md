# Arquitetura v1 — Agente de Gestão de Supermercado

## 1. Objetivo

O agente tem como objetivo auxiliar na gestão operacional de um supermercado, acompanhando entradas e saídas de estoque, identificando produtos próximos do estoque mínimo, planejando reposições de acordo com orçamento, custos, impostos e margem de lucro, e comunicando atividades aos funcionários.

O agente também acompanha o estoque de materiais de uso interno, como sulfite, bobinas, materiais de limpeza e outros insumos necessários para a operação.

A arquitetura busca utilizar a **menor autonomia necessária**: regras determinísticas são executadas por código, enquanto o modelo é utilizado quando existe necessidade de interpretação, planejamento ou decisão entre alternativas.

---

# 2. Entrada

## O quê

O sistema pode receber:

* mensagens de funcionários ou gestores em texto livre;
* atualizações de entrada de mercadorias;
* registros de venda/saída de produtos;
* atualizações de estoque;
* informações de fornecedores e preços;
* eventos automáticos do sistema de estoque;
* solicitações de compra;
* informações sobre orçamento disponível;
* alertas de estoque baixo.

## De onde e quem dispara

Existem dois tipos principais de disparo:

1. **Usuário:** gerente ou funcionário envia uma solicitação ao agente.
2. **Sistema:** eventos automáticos acordam o agente quando uma condição é atingida, como estoque abaixo do mínimo ou chegada de mercadoria.

## Heterogeneidade estimada

* ~35%: eventos automáticos de estoque e vendas;
* ~25%: consultas sobre estoque e produtos;
* ~15%: solicitações de compra/reposição;
* ~15%: comunicação e tarefas para funcionários;
* ~10%: consultas ou decisões financeiras/operacionais mais complexas.

Como existem diferentes tipos de entrada com comportamentos diferentes, **há justificativa para utilizar um Router**.

---

# 3. System

## System prompt

> Você é um agente de gestão operacional de supermercado. Você monitora estoque, auxilia no planejamento de reposição e comunicação de tarefas, mas não realiza compras ou outras ações financeiras irreversíveis sem respeitar as regras de orçamento e confirmação definidas pelo sistema.

## Ferramentas

| Ferramenta                 | Função                                                      | Tipo            | Reversível?                                    |
| -------------------------- | ----------------------------------------------------------- | --------------- | ---------------------------------------------- |
| `consultar_estoque`        | Consulta quantidade atual, estoque mínimo e máximo          | Leitura         | —                                              |
| `consultar_vendas`         | Consulta histórico e giro dos produtos                      | Leitura         | —                                              |
| `consultar_fornecedores`   | Consulta fornecedores, preços, impostos, prazos e condições | Leitura         | —                                              |
| `consultar_orcamento`      | Consulta orçamento disponível e fluxo de caixa              | Leitura         | —                                              |
| `calcular_reposicao`       | Calcula quantidade recomendada considerando giro e estoque  | Leitura/cálculo | —                                              |
| `calcular_custo`           | Calcula custo total, impostos e margem estimada             | Leitura/cálculo | —                                              |
| `registrar_entrada`        | Registra mercadoria recebida no estoque                     | Escrita         | Reversível por estorno                         |
| `registrar_saida`          | Registra saída/consumo de estoque                           | Escrita         | Reversível por estorno                         |
| `criar_solicitacao_compra` | Cria uma solicitação de compra para aprovação               | Escrita         | Reversível/cancelável                          |
| `enviar_fornecedor`        | Envia solicitação de mercadoria ao fornecedor               | Escrita externa | **Não tratar como automaticamente reversível** |
| `enviar_funcionario`       | Envia uma atividade ou aviso para funcionário               | Escrita externa | Reversível apenas por nova comunicação         |
| `registrar_tarefa`         | Registra uma tarefa interna                                 | Escrita         | Reversível                                     |

### Regra para escritas

Ações de leitura e cálculo podem ocorrer automaticamente.

A criação de uma solicitação de compra pode ocorrer automaticamente apenas dentro dos limites de orçamento previamente configurados.

O **envio efetivo de um pedido ao fornecedor** exige confirmação humana na versão inicial, pois pode gerar compromisso financeiro.

# 4. Estado

O estado que precisa sobreviver entre as etapas inclui:

```json
{
  "objetivo": "...",
  "rota": "...",
  "produto": "...",
  "estoque_atual": 0,
  "estoque_minimo": 0,
  "giro_medio": 0,
  "quantidade_recomendada": 0,
  "fornecedor_selecionado": "...",
  "custo_estimado": 0,
  "impostos_estimados": 0,
  "margem_estimada": 0,
  "orcamento_disponivel": 0,
  "tarefas_criadas": [],
  "falhas": [],
  "acoes_executadas": []
}
```

O texto original do usuário não precisa atravessar todas as etapas. O Router extrai as informações relevantes e as etapas seguintes trabalham com o estado estruturado.

---

# 5. Orçamento e limites

Para a primeira versão:

* **Máximo de passos do agente:** 8;
* **Máximo de sub-tarefas do agente:** 5;
* **Máximo de rodadas do avaliador:** 3;
* **Máximo de tentativas por ferramenta:** 2;
* **Tempo máximo de execução:** 60 segundos;
* **Orçamento máximo por solicitação de compra automática:** R$ 500;
* **Limite de comprometimento financeiro sem aprovação humana:** R$ 500;
* **Acima desse limite:** exigir aprovação do gerente;
* **Número máximo de mensagens enviadas automaticamente em uma execução:** 10.

Caso algum limite seja atingido, o agente deve interromper a ação e retornar o estado atual para revisão.

# 6. Processamento

## Fluxo

```text
1. ENTRADA
   recebe evento ou mensagem
   [—]

2. TRIAGEM
   identifica o tipo de solicitação
   [ROUTER]

       estoque/consulta
           -> consulta de dados

       reposição/compra
           -> planejamento de compra

       funcionário
           -> comunicação/tarefa

       entrada/saída
           -> registro de movimentação

       complexo/ambíguo
           -> agente

       fora do escopo
           -> recusa

3. COLETA
   busca estoque, vendas, fornecedores e orçamentos
   [— / ferramentas]

4. DECISÃO OPERACIONAL
   interpreta os dados e define a ação necessária
   [AGENTE — máximo 8 passos / 5 sub-tarefas]

5. VALIDAÇÃO
   verifica estoque, orçamento, custos, impostos e margem
   [AVALIADOR — máximo 3 rodadas]

6. EXECUÇÃO
   registra a movimentação, cria tarefa ou prepara solicitação
   [ESCRITA]

   compra acima do limite
       -> confirmação humana

   compra dentro do limite configurado
       -> solicitação pode ser criada automaticamente

7. COMUNICAÇÃO
   informa fornecedor ou funcionário quando autorizado
   [ESCRITA — envio externo]

8. RETORNO
   apresenta o resultado ao gerente/funcionário, podendo ser um aceite ou nova oferta (voltando a etapa de DECISÃO OPERACIONAL)
   [—]
```

## 4. DECISÃO OPERACIONAL [AGENTE]

**Entra:**

Os dados estruturados de estoque, vendas, fornecedor, custos e orçamento.

**Sai:**

```json
{
  "decisao": "comprar",
  "quantidade": 80,
  "fornecedor": "Fornecedor A",
  "custo_estimado": 1628.00,
  "motivo": "estoque abaixo do mínimo e giro elevado",
  "requer_aprovacao": true

```

O agente não recebe novamente o texto original do usuário. Ele trabalha sobre os dados relevantes já extraídos.

---

## 5. VALIDAÇÃO [AVALIADOR]

**Entra:**

```json
{
  "decisao": "comprar",
  "quantidade": 80,
  "custo_estimado": 1628.00,
  "orcamento_disponivel": 1200.00,
  "margem_estimada": 0.18
}
```

**Sai:**

```json
{
  "aprovado": false,
  "motivos": [
    "custo acima do orçamento disponível"
  ],
  "acao": "solicitar_aprovacao_gerente"
}
```

O avaliador impede que uma decisão aparentemente correta do agente seja executada quando viola orçamento, margem ou outra regra de negócio.

---

## 6. EXECUÇÃO [ESCRITA]

**Entra:**

```json
{
  "acao": "solicitar_aprovacao_gerente",
  "quantidade": 80,
  "fornecedor": "Fornecedor A",
  "custo_estimado": 1628.00
}
```

**Sai:**

```json
{
  "status": "aguardando_aprovacao",
  "solicitacao_id": "COMPRA-4821"
}
```

A escrita é registrada com um identificador idempotente para evitar duplicidade.

---

## 7. COMUNICAÇÃO [ESCRITA]

**Entra:**

```json
{
  "destinatario": "gerente",
  "solicitacao_id": "COMPRA-4821",
```

## 8. RETORNO

**Entra:**

O resultado da execução.

**Sai:**

Texto curto para o usuário.

Exemplo:

> O arroz está abaixo do estoque mínimo. A reposição recomendada é de 80 unidades, mas o custo estimado de R$ 1.628 excede o limite automático. A compra foi enviada ao gerente para aprovação.

# 8. Exemplo de outro fluxo: funcionário

Uma entrada como:

```text
"Chega uma carga de bebidas às 15h. Avise alguém para receber e depois mande repor as bebidas."
```

passaria pelo Router para a rota de **comunicação/tarefa**.

O agente produziria:

```json
{
  "tarefas": [
    {
      "tipo": "recebimento",
      "horario": "15:00",
      "descricao": "Receber carga de bebidas"
    },
    {
      "tipo": "reposicao",
      "descricao": "Repor bebidas após conferência da carga"
    }
  ]
}
```

Depois da validação:

```json
{
  "tarefas_aprovadas": true,
  "mensagens": 2
}
```

E o sistema registraria/enviaria as tarefas aos funcionários responsáveis.

O mesmo fluxo pode ser utilizado para materiais internos, como:

```text
"Está acabando o sulfite."
```

Nesse caso, o produto pertence ao estoque de **insumos internos**, mas utiliza as mesmas etapas de consulta, cálculo e reposição.

# 9. Justificativa dos padrões

## ROUTER

**Por que usar:** existem entradas heterogêneas — estoque, compras, movimentações, comunicação com funcionários e consultas. Cada tipo segue um fluxo diferente.

**Por que um workflow simples não resolve:** um workflow fixo teria dificuldade para decidir qual fluxo executar a partir de eventos e mensagens de naturezas diferentes. O Router é a primeira camada de decisão necessária.

**Ponto da tabela de decisão:** paramos no Router porque a entrada realmente precisa ser classificada antes de definir o processamento.

---

## AGENTE

**Por que usar:** decisões de reposição podem exigir combinar estoque atual, histórico de vendas, prazo do fornecedor, orçamento, custos, impostos e margem, além de decompor a tarefa em subtarefas.

**Por que um Router não resolve:** o Router consegue escolher o caminho, mas não consegue, sozinho, planejar uma decisão que depende de várias consultas e passos. O agente entra somente nessa parte mais complexa.

**Teto:** máximo de 8 passos e 5 sub-tarefas.

---

## AVALIADOR

**Por que usar:** uma compra pode parecer adequada ao agente, mas ainda violar orçamento, margem, estoque máximo ou outras regras de negócio. Uma segunda etapa independente verifica a decisão antes da execução.

**Por que o agente sozinho não resolve:** deixar o mesmo agente gerar e validar a própria decisão aumenta o risco de uma decisão incorreta chegar à etapa de escrita. O avaliador cria uma barreira antes das ações de maior impacto.

**Teto:** máximo de 3 rodadas de avaliação.

---

# 10. Escritas e reversibilidade

As principais escritas do sistema são:

```text
REGISTRAR ENTRADA DE MERCADORIA
    escrita
    reversível por estorno

REGISTRAR SAÍDA
    escrita
    reversível por estorno

CRIAR PLANEJAMENTO DE COTAÇÃO
    escrita

CRIAR SOLICITAÇÃO DE COMPRA
    escrita
    cancelável antes do envio

ENVIAR PEDIDO AO FORNECEDOR
    escrita externa
    potencialmente irreversível
    confirmação humana na v1
    correção possível por nova mensagem

CRIAR ANALISE DE TOMADA DE DECISÃO
    escrita
    correção possível por nova mensagem 

ENVIAR TAREFA AO FUNCIONÁRIO
    escrita externa
    correção possível por nova mensagem

REGISTRAR TAREFA
    escrita
    reversível
```

A versão inicial evita que o agente realize automaticamente uma ação financeira irreversível sem confirmação humana.

---

# 11. Saída final para o usuário

A saída deve ser curta e informar principalmente:

1. o que foi identificado;
2. qual decisão foi tomada;
3. qual ação foi executada;
4. se existe alguma pendência ou aprovação necessária.

Exemplo:

> **Estoque baixo:** arroz 5 kg.
> Reposição recomendada: 80 unidades.
> Compra de R$ 1.628 aguarda aprovação do gerente porque excede o limite automático.

# 12. Resumo da arquitetura

```text
                     ┌──────────────────┐
                     │     ENTRADA      │
                     │ mensagem/evento  │
                     └────────┬─────────┘
                              │
                              ▼
                     ┌──────────────────┐
                     │     ROUTER       │
                     │  classificação   │
                     └────────┬─────────┘
                              │
              ┌───────────────┼────────────────┐
              │               │                │
              ▼               ▼                ▼
        consulta         comunicação       reposição
              │               │                │
              │               │                ▼
              │               │         ┌──────────────┐
              │               │         │    AGENTE    │
              │               │         │ max. 8 passos│
              │               │         └───────┬──────┘
              │               │                 │
              │               │                 ▼
              │               │         ┌──────────────┐
              │               │         │  AVALIADOR   │
              │               │         │ max. 3 rounds│
              │               │         └───────┬──────┘
              │               │                 │
              └───────────────┴─────────────────┤
                                                ▼
                                      ┌──────────────────┐
                                      │     ESCRITAS     │
                                      │ estoque/tarefas/ │
                                      │    compras       │
                                      └────────┬─────────┘
                                               │
                                               ▼
                                      ┌──────────────────┐
                                      │     RETORNO      │
                                      └──────────────────┘
```

A arquitetura v1, portanto, utiliza **Router para decidir o tipo de problema, Agente para decisões operacionais que exigem planejamento e Avaliador para validar decisões antes de ações de maior impacto**. As operações simples de consulta, cálculo e registro permanecem determinísticas e não utilizam autonomia desnecessária.
